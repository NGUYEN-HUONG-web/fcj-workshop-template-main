## 1. Overall Experience

The **First Cloud AI Journey – AWS Workforce Bootcamp** gave me an opportunity to learn AWS through hands-on activities and apply that knowledge to a specific product.

The combination of worklogs, blog posts, technical events, team activities, and a final project helped me learn about AWS services while developing my ability to:

- Research technical documentation independently.
- Document my learning process.
- Solve technical problems.
- Collaborate with a team.
- Present results clearly.
- Evaluate completed work and identify remaining limitations.

One aspect I particularly appreciated was the program’s emphasis on independent learning and problem-solving.

Instead of focusing only on theory, I had opportunities to work directly with technologies and services such as:

- Docker.
- Amazon EC2.
- Amazon EBS.
- Amazon S3.
- AWS Identity and Access Management.
- Amazon CloudWatch.
- AWS Budgets.
- Retrieval-Augmented Generation.

By deploying the RAG Chat project, I was able to validate what had been completed, identify limitations in the current architecture, and propose future improvements.

## 3. Challenges

### 3.1 Large Volume of Material

The program covered a significant amount of content related to AWS, Docker, RAG, and application deployment.

At the same time, the time available for learning, implementation, testing, and report completion was limited.

Several topics require more in-depth study, particularly:

- System security.
- Secret management.
- Backup and recovery.
- Centralized monitoring.
- RAG quality evaluation.
- Scalable architecture.

### 3.2 Deployment Troubleshooting

Some errors appeared only when building Docker images or deploying the application to EC2.

Troubleshooting often required checking multiple layers:

```text
Source code
→ Docker image
→ Docker container
→ Service port
→ Security Group
→ EC2
→ EBS
→ IAM
→ Related AWS services
```

Identifying the root cause sometimes took a significant amount of time because an issue could come from configuration, permissions, network connectivity, or the runtime environment.

### 3.3 Collecting Technical Evidence

Technical evidence was sometimes collected too late.

As a result, some tests did not have complete before-and-after screenshots, including:

- Persistence testing.
- Container restart testing.
- Data backup testing.
- Data restore testing.
- IAM permission verification.
- Cost alert verification.

For future projects, I should define the required evidence in advance and save the results immediately after each test.

### 3.4 Costs and Service Quotas

Cloud costs and external service quotas need to be monitored throughout the testing process.

Without proper controls, unused resources may continue to incur costs.

I need to pay closer attention to:

- EC2 instance status.
- EBS storage usage.
- Data stored in Amazon S3.
- Network traffic.
- AI model quotas.
- Budgets and cost alerts.
- Resources that are no longer in use.

## 4. Suggestions for the Program

### 4.1 Offer More In-Office Attendance Days

I recommend offering more days or time slots for students to register for in-office participation.

The program has a relatively large number of participants, but the number of available days and approved attendance slots is limited. This makes it difficult for many students to schedule an opportunity to experience the workplace in person.

Adding more days or time slots could:

- Provide fairer access for students.
- Allow students to meet mentors in person.
- Increase communication among project teams.
- Help resolve technical problems more quickly.
- Give students direct workplace experience.
- Create more opportunities for networking and peer learning.

### 4.2 Provide Learning Paths for Different Experience Levels

The program could provide learning paths based on participants’ backgrounds and experience levels.

For example:

- An introductory AWS path for students with no cloud experience.
- An introductory DevOps path for students from AI or Data backgrounds.
- An AI and RAG path for students with software development experience.
- Advanced content for students who already have AWS certifications or professional experience.

This structure could help participants build the required foundation before beginning more complex projects.

### 4.3 Organize More Hands-on Workshops

The program could offer additional workshops or labs on:

- Terraform.
- AWS Lambda.
- Amazon API Gateway.
- CI/CD.
- AWS Secrets Manager.
- Amazon CloudWatch.
- Backup and disaster recovery.
- Container security.
- Serverless architecture.
- RAG evaluation.

Topic-specific hands-on sessions would help participants understand how to apply these services to real projects.

### 4.4 Create More Opportunities for Presentations and Discussion

The program could organize additional sessions where participants can:

- Present project progress.
- Share errors they encountered.
- Explain solutions they tested.
- Receive feedback from mentors.
- Learn from other teams’ approaches.
- Practice technical presentation skills.

### 4.5 Expand Peer Learning Activities

Participants with different backgrounds and skill levels could be paired to support peer learning.

For example:

- Students with AWS experience could help with cloud configuration.
- Students with AI experience could help with RAG and model integration.
- Students with programming experience could help with application development.
- Students with DevOps experience could help with Docker and CI/CD.

This approach could support project delivery while helping each participant improve their communication and teamwork skills.
